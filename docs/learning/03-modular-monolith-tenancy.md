# 03 — Modular monolith in practice: tenancy, row-level security, audit

**Week 2 → gate G1.** The first real business code: tenants, the plant/line/asset hierarchy, sensor mappings, an
append-only audit trail, and an Angular asset explorer, all behind Keycloak login and tenant isolation.

## Concepts you will meet

*(Written before the week's code, as CLAUDE.md requires.)*

- **Schema per module** — each module owns one PostgreSQL schema and one EF Core `DbContext`; nothing else
  touches its tables. How EF Core keeps a migrations history per schema.
- **Multi-tenancy, three layers deep** (ADR-008) — why one layer is never enough:
  1. *Policy-based authorisation* decides **whether** a user may call an endpoint.
  2. *EF Core global query filters* decide **which rows** the application asks for.
  3. *PostgreSQL row-level security (RLS)* decides **which rows the database will return**, even if the
     application forgets the filter or someone writes raw SQL.
- **Session variables and `SET ROLE`** — how a request's tenant reaches the database (`set_config`), and why the
  application must not connect as a superuser if RLS is to mean anything.
- **Interceptors** — EF Core hooks that run on every connection open and every `SaveChanges`, so tenancy cannot be
  forgotten by a developer writing a new endpoint.
- **Append-only audit with a hash chain** — before/after hashes, a per-tenant chain where each record's hash
  includes the previous one, and a database trigger that makes `UPDATE`/`DELETE` impossible. Tamper-*evident*,
  not tamper-*proof*, and why that distinction matters in an interview.
- **One transaction across two modules** — writing the asset change and its audit record atomically without the
  Assets module knowing anything about the Audit module's internals (a contract in BuildingBlocks).
- **Optimistic concurrency** — PostgreSQL's `xmin` system column as a free row version; `409 Conflict` instead of
  lost updates.
- **Seeding from a specification** — the same `plant.yaml` drives the simulator (Python) and the asset registry
  (.NET): one source of truth, two languages, contracts not shared code.
- **Contract tests for an API** — the OpenAPI document is generated by the running app and compared with the
  committed copy in `contracts/`; an accidental API change fails CI.
- **Testing against a real database** — Testcontainers in CI, a local PostgreSQL when Docker is not available;
  why RLS cannot be tested with an in-memory provider.
- **Gate G1 as an automated end-to-end check** — `docker compose up`, a real Keycloak token, a real API call.

## 1. One module, one schema, one `DbContext`

Each module owns a PostgreSQL schema (`assets`, `audit`, …) and a `DbContext` that maps only into it. The rule is
enforced, not hoped for: the architecture test `A_module_maps_only_into_its_own_schema`
([ModuleBoundaryTests.cs](../../src/platform-api/tests/SmartFactory.Platform.ArchitectureTests/ModuleBoundaryTests.cs))
builds every module's EF model offline and fails if an entity lands in another schema.

Two details make it work in practice:

- **A migrations history per schema.** EF Core normally keeps one `__EFMigrationsHistory` table. With several
  contexts in one database they would fight over it, so each module stores its history in
  `{schema}.__ef_migrations_history` ([PersistenceExtensions.cs](../../src/building-blocks/SmartFactory.BuildingBlocks/Persistence/PersistenceExtensions.cs)).
  Splitting a module into its own service later means moving one schema and its history, nothing else.
- **Only one public type per module.** `AssetsModule` and `AuditModule` are the whole public surface; entities,
  DTOs and the `DbContext` are `internal`. Another module literally cannot compile code against them.

**Why not one big `DbContext`?** It is simpler on day one and a trap on day ninety: any module can join any table,
and the "seam" you wanted to cut later is gone. **Why not microservices now?** See note 01: one deployable, one
transaction, one debugger session, and the seams are already drawn.

## 2. Tenancy, three layers deep

| Layer | Where | What it stops |
|---|---|---|
| Policy-based authorisation | `TenantMember`, `Administrator`… policies on every endpoint group | A token without a `tenant_id` claim, or a technician calling an admin endpoint |
| EF Core global query filters | [TenantAwareDbContext.cs](../../src/building-blocks/SmartFactory.BuildingBlocks/Persistence/TenantAwareDbContext.cs) adds `WHERE tenant_id = @tenant` to every `ITenantScoped` entity | A developer forgetting the `Where` |
| PostgreSQL row-level security | Policies created in each module's first migration ([RowLevelSecuritySql.cs](../../src/building-blocks/SmartFactory.BuildingBlocks/Persistence/RowLevelSecuritySql.cs)) | Raw SQL, a bug in EF, a future reporting query |

The layers fail differently, which is the point. A missing filter is caught by RLS; a mis-written policy is caught
by the filter; and the test suite proves each layer *on its own*:
[RowLevelSecurityTests.cs](../../src/platform-api/tests/SmartFactory.Platform.Api.Tests/Tenancy/RowLevelSecurityTests.cs)
bypasses EF entirely and runs raw SQL as the application role.

Writes are covered too. `TenantStampingInterceptor` stamps `tenant_id` on new rows and throws if code tries to
save a row for another tenant, and the RLS policy's `WITH CHECK` makes the database reject it anyway
(error `42501`, tested).

**A foreign id answers 404, never 403.** A 403 would confirm that the record exists in some other tenant.
[CrossTenantAuthorizationTests.cs](../../src/platform-api/tests/SmartFactory.Platform.Api.Tests/Tenancy/CrossTenantAuthorizationTests.cs)
attacks every endpoint from tenant B with tenant A's ids. Both tenants hold the *same* plant with the *same*
asset codes, so a leak cannot hide behind "the names looked different". A fitness test in the same file fails when
someone adds an endpoint without adding it to the attacked list.

## 3. How the tenant reaches the database: `SET ROLE` and `set_config`

PostgreSQL does not know about HTTP requests. On every connection open,
[TenantSessionInterceptor.cs](../../src/building-blocks/SmartFactory.BuildingBlocks/Persistence/TenantSessionInterceptor.cs) runs:

```sql
SET ROLE "sf_app";
SELECT set_config('app.tenant_id', @tenant, false);
```

and the policies compare rows with `NULLIF(current_setting('app.tenant_id', true), '')`. No tenant set means
`NULL`, and `tenant_id = NULL` is never true: **no tenant, no rows**. The safe default is the empty result.

Why `SET ROLE`? **Superusers and table owners bypass RLS.** The connection logs in as the owner (it has to, to run
migrations), then drops to `sf_app`, a `NOLOGIN` role with only `SELECT/INSERT/UPDATE/DELETE` grants. `FORCE ROW
LEVEL SECURITY` is on as a second guard. Migrations run inside `ElevatedDatabaseScope`, which issues `RESET ROLE`
instead. In Azure (week 9) the app will log in as a non-owner directly and migrations will run from the pipeline.

The tenant itself comes from the `tenant_id` claim (Keycloak mapper), or from `TenantScope.Begin(...)` for
background work such as seeding. It is an `AsyncLocal`, so it flows through `await` without being passed around.

## 4. The audit trail: append-only, hash-chained, same transaction

Every change writes an `AuditEvent`
([AuditEvent.cs](../../src/platform-api/Modules/SmartFactory.Modules.Audit/Domain/AuditEvent.cs)) with the actor,
the before/after state as JSON, a SHA-256 of each, the trace id as correlation id, and a **chain hash**: the
SHA-256 of this record's fields *plus the previous record's chain hash* for the same tenant.

- **Append-only, enforced by the database.** A trigger rejects `UPDATE`, `DELETE` and `TRUNCATE` on
  `audit.audit_events`, even for the owner; `sf_app` has no such grants in the first place. Both are tested.
- **Tamper-evident, not tamper-proof.** Someone with owner rights can disable the trigger and edit a row. They
  cannot do it *unnoticed*: `GET /api/audit/verify` recomputes the chain and reports the first broken sequence.
  [AuditTrailTests.cs](../../src/platform-api/tests/SmartFactory.Platform.Api.Tests/Audit/AuditTrailTests.cs) does
  exactly that attack. To be tamper-*proof* you would anchor the chain head somewhere the attacker cannot write
  (WORM storage, a signed log); that is Release 2.
- **Ordering under concurrency.** Two writes for one tenant at the same moment must not both chain from the same
  predecessor. `pg_advisory_xact_lock(hashtextextended(tenant, 0))` serialises writers per tenant only, and is
  released automatically at commit.
- **One transaction across two modules.** The Assets module must not know the Audit module's tables. It depends
  on `IAuditTrail` in BuildingBlocks and passes its open `DbConnection` and `DbTransaction`
  ([AssetsUnitOfWork.cs](../../src/platform-api/Modules/SmartFactory.Modules.Assets/Persistence/AssetsUnitOfWork.cs)).
  The audit context enlists in that transaction, so the asset change and its record commit or roll back together.
  Writing the audit *after* commit would leave a window where a crash loses the record forever.
- **Timestamps are truncated to microseconds** before hashing, because .NET ticks are 100 ns and PostgreSQL stores
  µs: without it, the hash computed at write time would never match the one recomputed from the database.

## 5. Optimistic concurrency with `xmin`

PostgreSQL gives every row version a system column `xmin` (the creating transaction id). Mapped with
`IsRowVersion()`, EF adds `WHERE xmin = @original` to every `UPDATE`. The API returns it as `version`; a client that
sends a stale version gets **409 Conflict** instead of silently overwriting someone else's change. No extra column,
no trigger. Tested in `AssetsApiTests`.

## 6. One plant specification, two languages

`docs/plant/plant.yaml` drives the simulator (Python, week 5) and now the asset registry (.NET,
[PlantSeeder.cs](../../src/platform-api/Modules/SmartFactory.Modules.Assets/Seeding/PlantSeeder.cs)). Nothing is shared
but the file, which is ADR-001's "contracts, not shared code". The seeder is idempotent (re-running creates 0
records, tested), refuses a spec without `synthetic: true`, and audits what it creates as actor `system:seed`.

## 7. The API contract is a file in the repository

The running app generates its OpenAPI document; [OpenApiContractTests.cs](../../src/platform-api/tests/SmartFactory.Platform.Api.Tests/Contracts/OpenApiContractTests.cs)
compares it with [`contracts/openapi/platform-api.v1.json`](../../contracts/openapi/platform-api.v1.json). Renaming a
DTO property fails CI until the contract file is regenerated (`SF_UPDATE_CONTRACTS=1 dotnet test …`) and the diff
is reviewed in the pull request. The Angular models in
[assets.api.ts](../../src/web/src/app/features/assets/assets.api.ts) are written against that file.

## 8. Testing against a real database

RLS, triggers, advisory locks and `xmin` do not exist in EF's in-memory provider or SQLite, so a test there would
prove nothing about them. The integration tests start the real API (`WebApplicationFactory`) on a real
PostgreSQL 16: Testcontainers in CI, or any server you point `SF_TEST_POSTGRES` at locally (a throw-away database
is created and dropped). Authentication is replaced by a header-driven test handler; **everything after
authentication is production code**.

## 9. The asset explorer: signals all the way down

[asset-list.ts](../../src/web/src/app/features/assets/asset-list.ts) uses `httpResource`: a signal that re-fetches
whenever the signals it reads change. The filter form is a typed reactive form; its debounced value becomes a
signal, the request is computed from it, and the template reads `assets.value()`, `assets.isLoading()` and
`assets.error()`. No subscriptions to manage, no `async` pipe. The detail page shows each sensor's MQTT topic:
the platform's read-only side of the OT boundary made visible.

## 10. Gate G1 is a script, not a feeling

"docker compose up → login → asset list" is checked by
[`scripts/g1-check.sh`](../../scripts/g1-check.sh) (curl: 401 without a token, a real Keycloak token, tenant
claim, the 8 seeded machines, CORS, SPA deep links) and
[`scripts/g1-browser-check.cjs`](../../scripts/g1-browser-check.cjs) (Chromium signs in on Keycloak's own page
with PKCE, opens the explorer and the detail page, keeps a screenshot). CI runs both on a fresh stack.

One Compose subtlety: the browser reaches Keycloak at `localhost:8180`, the API container at `keycloak:8080`.
Tokens carry the issuer the browser saw, so the API validates `Authority = http://localhost:8180/...` but downloads
keys from `MetadataAddress = http://keycloak:8080/...`.

## 11. Pitfalls met this week (and what they teach)

- **"fail: Failed executing DbCommand … __ef_migrations_history does not exist"** on a fresh database. Harmless:
  EF probes for its history table before creating it and logs the probe's failure. Lesson: read a log line's
  *source* before reacting to its level.
- **Seeded children silently missing.** Adding entities only through a navigation collection on an already-tracked
  parent did not always mark them `Added`. The seeder now calls `db.X.Add(...)` explicitly. Explicit beats clever.
- **A test that passed alone and failed in CI.** The plants test counted assets per line, while another test in
  the same collection had added an asset to that line first. Shared fixtures need tests that do not depend on
  order: the test now seeds its own tenant.
- **Migrations tripped the analyzers** (CA1861) because generated code is not ours to restyle;
  `generated_code = true` in `.editorconfig` fixed CI, and then the *Docker* build failed the same way because
  the Dockerfile did not copy `.editorconfig`. The image must build with the same settings as CI.
- **A health check that could never pass.** The image's `HEALTHCHECK` ran the app with `--health-probe`, which
  nothing handled, so Docker started a second server every 15 s. Nobody noticed in week 1 because nothing
  *waited* on that health status; the first `depends_on: service_healthy` exposed it. A check that has never been
  seen to fail has not been tested.
- **The gate found a week-1 bug nobody could see.** The realm export declared its own `clientScopes` (`tenant`,
  audience), and Keycloak then created *none* of its standard ones. Tokens carried `tenant_id` but no `sub`, no
  username and no roles, so every role-protected endpoint would have answered 403 to a real user. The unit and
  integration tests could not notice, because they replace Keycloak with a test handler. Only a real token through
  the real stack showed it, which is exactly what an end-to-end gate is for. The fix spells the standard scopes out
  in the export.
- **A commit scope used in CLAUDE.md's own example (`test(authz)`) was not in the allowed list.** Documentation and
  enforcement drift apart unless one is generated from the other.

## Interview answer (two sentences)

"Tenant isolation is enforced in three independent layers (authorisation policies, EF Core global filters and
PostgreSQL row-level security, with the app dropping to a non-owner role on every connection), and the test suite
attacks every endpoint from a second tenant with identical data and also runs raw SQL as the app role. Every change
writes a hash-chained audit record in the same transaction through a contract, so the module boundaries hold and
tampering is detectable, which is an honest claim, unlike tamper-proof."
